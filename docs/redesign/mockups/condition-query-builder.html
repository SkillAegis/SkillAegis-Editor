Building a data_filtering rule without writing jq

The power of data_filtering is real, but authors currently express it as a raw jq pipeline — easy to get wrong, hard to read back. Every complex rule is really a small query with three moves. If the tool knows those moves, it can write the jq so the author never has to.

The expression you flagged as overwhelming [.Event.Object[].Attribute[], .Event.Attribute[]] | .[] | select(.value == "194.78.89.250").to_ids
from every attribute in the event where value is 194.78.89.250 check its to_ids flag

Every scary rule is the same three moves

I extracted every jq path from your shipped scenarios. The complex ones never vary in structure — they only vary in which collection, which filter, and which field. Name those three slots and the jq becomes a by-product.

MoveAuthor picksGenerated jq
FROM “Every attribute in the event” [.Event.Object[].Attribute[], .Event.Attribute[]] | .[]
WHERE “value is 194.78.89.250” (optional) select(.value == "194.78.89.250")
CHECK “its to_ids flag” .to_ids

The two tabs above are working prototypes of this idea. ① Guided query builder gives authors the three slots as dropdowns. ② Point at the data flips it around: click the value in a real event and the tool writes the path for you. Both keep the raw jq editor as an escape hatch, and both preview the generated jq live — try them.

Why this is safe to build

None of this changes the CEXF data model or the evaluation engine — it only changes how a condition's path string is authored. The generated jq is identical to what authors write by hand today, and you already have the plumbing:

  • the visual condition builder (ConditionRow.vue) already owns the operator + values half of a condition;
  • the /injects/jq-path-test endpoint already compiles a path against sample data and returns the extracted value or the error — that powers the live preview and validation for free;
  • anything the builder can't express round-trips to the existing raw jq/JSON editor.
